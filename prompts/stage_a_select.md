你是一名资深测试开发。下面是我的一批功能测试用例。
请逐条判断它是否适合做自动化，并严格按以下规则：

【适合自动化 适合】(规则编号 S1~S5)
S1. 高频执行：冒烟测试、核心业务主路径、回归必跑用例
S2. 用例稳定：需求已冻结，UI/接口短期内不变
S3. 数据驱动：同一逻辑需用多组数据验证
S4. 结果可自动断言：预期结果能用代码精确判断（有明确返回值/状态码/DB记录/页面元素）
S5. 前置条件可程序化构造（能用API/DB/脚本准备数据，不依赖人工）

【不适合自动化 不适合】(规则编号 N1~N5)
N1. 一次性、探索性、主观体验/视觉判断类
N2. UI频繁变动的页面
N3. 依赖验证码、人脸识别、短信、物理设备、第三方人工审核
N4. 预期结果模糊、无法机器断言（如"页面美观""提示友好"）
    反例：预期中已含具体定位器(XPath/CSS/元素属性)+可见性/文本断言条件的，不得判N4
N5. 前置条件无法自动构造

【输出格式】表格：用例编号 | 测试标题 | 判定(适合/不适合/部分适合) | 判定理由(对应上面哪条规则) | 改造建议(若部分适合，说明如何改造才能自动化)

【强制】判定理由必须明确写出规则编号（适合类用 S1~S5，不适合类用 N1~N5），禁止只给漂亮结论。

【附加】表格之后，再以 JSON 数组形式输出同样结论，供程序读取（字段固定，不要增删）：
- verdict 只能三选一："适合" / "不适合" / "部分适合"，禁止照抄本说明文字
- rule 填规则编号字符串："S1"~"S5" 或 "N1"~"N5"，例如判"适合"且依据适合类第1条就填 "S1"
- JSON 数组必须包含输入的全部用例，一条都不能少
[{"case_id":"TC-001","verdict":"适合","rule":"S1","suggestion":""}, ...]
